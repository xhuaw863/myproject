# 门诊业务闭环审计(挂号分诊/就诊/处方医嘱/收费/发药/医技/数据一致性)

审计范围:`service/cashier`、`service/outpatient`、`service/doctor`、`service/pharmacy`、`service/warehouse`、`service/medtech` 等门诊主链路,只读核查。

**整体成熟度:中上(约 3.5/5)**。门诊主链路(挂号→接诊→开方→收费→发药→执行)已闭环;状态机设计最扎实(4/5),资金与账务正确性(2.5/5)与医保一致性(2/5)是短板。**真实医保环境与多窗口并发下"会出钱/出合规事故"的 P0 集中在收费并发与医保外部调用顺序。**

## P0

### P0-1 收费并发双收费:查检与回写之间无锁、无唯一约束
- 位置:`CashierService.java:403-422,457,573`(doCharge 先 SELECT charge_status=0 无 FOR UPDATE,573 行无条件 UPDATE charge_status=1);his_charge_bill 仅 (tenant_id, bill_no) 唯一键,visit_id 无唯一索引
- 触发:同一就诊两个窗口同时收费(或连点重试)→ 双 SF 单、双 2207 结算(mock 恒成功)→ **患者收两次费、医保结算两笔**。
- 修复:收费前置 `SELECT ... FOR UPDATE` 锁 visit 行;加 UNIQUE(tenant_id, visit_id, bill_type) 兜底;回写改条件更新 `WHERE charge_status=0`,affected=0 回滚。

### P0-2 并发全额退费双退 + 全额/部分退费互斥失效
- 位置:`CashierService.java:649,656-683,686-703,757,799-826`(refund/partialRefund 均 check-then-act;2208 先于本地操作;MockYbServer 2208 恒成功放大窗口)

- 修复:原单行 `SELECT ... FOR UPDATE` 或条件更新 `SET status=2 WHERE id=? AND status=1` 按 affected 判成败;全额退时同步全部明细 refunded_qty=qty(与部分退共享余量口径)。

### P0-3 挂号状态机断裂:已就诊状态(3)从不落库,结算后退号窗口无限
- 位置:`HisRegistrationService.java:286-288`(cancel 仅校验 status==1);全库无任何地方写 status=3

### P0-4 未收费处方可发药(漏费)

- 修复:doDispense 前置校验 visit.charge_status=1(2 也拒绝);todoPage 同口径过滤。

## P2(择要)

- 日结并发 check-then-insert 抛 DuplicateKeyException(唯一键兜底但报错不友好);可对"明天"做日结
- 单号生成回绕与多实例撞号:`generateBillNo`(Math.floorMod %10000)、HisOrderService.genNo(%1000)、generatePatientNo 等统一"内存序号+DB 回读"模式,单实例安全、多实例必撞
- 候诊序号当日 MAX+1 并发重号无唯一键
- 部分退费期间原发票不红冲;RefundReq.amount 定义但未使用
- 医技侧幂等 check-then-insert 无唯一约束(ExamReportService.createDraft/SpecimenService.generateSpecimens/saveRecord 并发双建病历)
- 病历无就诊状态/收费校验,已诊毕已退费病历可继续修改无留痕
- 输入枚举校验缺失(挂号 payMethod、处方 rxType 任意字符串直存)
- HisMedicalTemplateService.update/delete 无归属校验,可改删他人模板
- HisOrder.status 语义混乱(注释"3-已退"与实际使用不一致,TreatmentPlanService:89 按 status=3 判"已退"永远不成立)

## 正面确认项

- 金额字段全链路 BigDecimal、DECIMAL 落库,无 double/float;部分退费尾差收口(870-880)正确
- 库存扣减 `qty>=?` 乐观锁 + 3 轮 FIFO 重试 + upsertStock 唯一键冲突原子累加,防超扣防双插思路正确
- 发药/治疗/护士执行/标本/危急值/报告双签全链路条件更新乐观锁状态机
- 收费状态机口径统一(visit.charge_status + bill.status + billType),日结锁定退费边界(672-674)设计合理
- 处方服务端按药房维度重算价、改派强制 charge_status=1
- 退费单复制原单明细、负向支付明细、发票红冲留痕完整
