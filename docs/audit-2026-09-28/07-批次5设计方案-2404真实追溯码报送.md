## 三、总体架构:采集校验 → 发药绑定 → 2404 报送状态机

```
入库采集 collect() ──[+20位格式/药品一致性 服务端校验]──▶ status=0 在库
发药绑定 bind() / 药房台 trace-scan ──▶ status=1 已发药(挂 patient/visit/dispense)
      │
报送 upload(orgId,locationId)(手动/定时):
  T1(事务)   认领本批 status=1 且 upload_status∈{0,2} 的行 → 置 1(报送中) + upsert his_upload_status(biz_type=TRACE, biz_id=trace.id, status=0)
  T2(无事务) YbHttpClient.call("2404", buildTrace404Input(rows), insuplcAdmdvs)   [每批≤平台上限; 逐行或批量按规范]
  T3(事务)   按 T2 三分结果:
    SUCCESS(回执0) → 行 upload_status=9已报送 + upload_msgid/upload_batch_no=平台报文ID; his_upload_status=1
    FAIL(非0)      → 行 upload_status=2失败待补 + last_err; his_upload_status=2(退避重试)
    UNKNOWN(超时)  → 行留 1(报送中); his_upload_status=2; 不自动重发(2404 幂等待平台确认); Sweeper 到期按 msgid 经 txn_log 复核收敛
  mock 开关: -Dyb.mock.* 命中 → MockYbServer 2404 受理入库返假回执; 真实模式走签名链
```

**并发语义**:T1 认领用 `UPDATE ... WHERE upload_status IN(0,2)` affected-rows 抢占;窗口/定时并发下同一行仅一条链认领成功,不重复报送。

## 四、模块细化

### 4.1 采集校验(P1-6)
- `collect()`:对每个 `code` 服务端校验 `^\d{N}$`(N 及是否含字母/校验位待规范 §十#5 确认,默认 20 位),不合规则拒绝并计数返回;商品码/监管码归一为物理追溯码逻辑自前端下沉复核。
- 药品一致性:扫码带 `drugCatalogId` 时校验该码未绑定他药(uk 保证全局唯一即可,跨药重复直接按已存在拒绝)。
- 占位码 `genPlaceholderCode()`(86 开头 20 位)**仅 mock/演示**使用,真实模式须关闭(`collect` 拒绝纯占位来源)。

### 4.2 报送数据组装
- 从 `his_drug_trace_code` 取 `status=1 AND upload_status IN(0,2)` 行(可选 org/location 过滤);
- 逐行/批量映射 2404 报文字段(§八),销售流水键取 `dispense_id`/`visit_id`(映射待 §十#6 确认)。

### 4.3 状态机接入(复用 M5)
- `his_upload_status`:`biz_type='TRACE'`、`biz_id=trace.id`、`mdtrt_id` 冗余便于对账;status 流转 0→1(成功)/0↔2(失败/待补)/3(撤销:退药回库时)。
- `UploadStatusSweeper` 增 `TRACE` 分支:到期(next_retry)行重发 2404;退避递增;max6 转【医保上报告警】。
- 退药/报废(`updateStatus`→status=2/3):同步把对应 `his_upload_status` 置 3(已撤销),避免对已退货码继续报送。

### 12.2 【3505】商品销售 输入(表206,节点标识 `selinfo`,单行;3505A 表208 节点 `selinfoDetail` 多行、字段同)
