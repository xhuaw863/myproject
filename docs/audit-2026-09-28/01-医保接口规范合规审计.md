审计基准:根目录《湖北省医疗保障信息平台定点医药机构接口规范V1.2.02.pdf》(2026-02-26 发布,共 1515 页,对应国家平台基线 XJ-K01-2020 + 地方修订)。

## 一、总体结论

- 医保交易骨架(报文头组装/签名占位/出入参 DTO/交易编排)已按规范搭起,**但尚处于"开发期对齐"状态,离真实平台联调有 8 项 P0 级阻断**。
- 已实现的交易:2201/2202/2203/2204/2206/2207/2208(门诊)、1301~1307(目录下载)、2301~2305、2401/2402(住院半成品)。
- 未实现的交易(医保原生关键缺口):9001 签到、1101 人员信息获取、2001 待遇检查、2205 明细撤销、2601 冲正、3101~3103 明细审核、3201/3202 对账、3301 目录对照上传、3401 科室上传、9101 医保码。

## 二、P0 级问题(真实平台联调前必须修复)

### P0-1 数字签名未实现(假签名)
- 位置:`common/SignUtil.java:24-35、66-86`
- 问题:SM2 签名是 TODO 占位,实际返回的是 **SHA-256 摘要冒充 SM3**(`sm3Digest` 用 `MessageDigest.getInstance("SHA-256")`),`sm2Sign` 仅打日志返回摘要;签名异常时 `sign()` 捕获后**返回空串**,报文会带空 `cainfo` 发出。
- 规范依据:4.4「将报文剔除 cainfo、input 后,按照数据元标识的 ASCII 码递增排序…SM2 运算,即是数字签名信息(cainfo)的值」;湖北省平台验签必然失败,所有交易被拒。
- 修复方向:pom 已引入 bcprov-jdk15on,用 BouncyCastle 实现 SM2withSM3 签名(私钥签名、公钥验签),签名失败必须 fail-fast 抛错,不允许空签名出站。同时 `buildSignContent` 已正确剔除 cainfo/input 并按 TreeMap 升序拼接,签名原文逻辑保留即可。

### P0-2 参保地医保区划 insuplc_admdvs 缺失
- 位置:`common/YbHttpClient.java:110-112`(仅当入参非空才放入报文);全部业务调用方(`OutpatientService` 各方法)均未传该参数。
- 规范依据:表3「insuplc_admdvs 参保地医保区划:如果交易输入中含有人员编号,此项必填,可通过【1101】人员信息获取交易取得」。2201/2206/2207 输入均含 psn_no → 必填。
- 修复方向:业务链路从患者参保信息(`his_patient_insu.insuplc_admdvs`,数据模型已备)取参保地传入;`YbHttpClient.call(infno,input)` 应在 input 含 psn_no 而参保地为空时直接抛错,防止漏传。

### P0-3 2207 门诊结算必填字段缺失(结算请求必被拒)
- 位置:`service/cashier/CashierService.java:489-498` 组装 `SettlementReq` 仅设置 psn_no/mdtrt_id/insutype/med_type/medfee_sumamt/psn_setlway/mdtrt_cert_type。
- 规范依据(表115 输入,必填 Y):`mdtrt_cert_no`(Y)、`chrg_bchno` 收费批次号(Y)、`acct_used_flag` 个人账户使用标志(Y)、`fulamt_ownpay_amt`(Y)、`overlmt_selfpay`(Y)、`preselfpay_amt`(Y)、`inscp_scp_amt`(Y)全部未传。
- 修复方向:收费前计算四个自费/自付口径金额(与票据式样字段 selfCost/outOfScope 同源:乙类先自付+丙类/自费全自费=fulamt_ownpay_amt 口径按规范定义);生成 chrg_bchno(收费批次号,同批次明细共用一个批次号,30 位内);acct_used_flag 按个人账户使用策略传 0/1;mdtrt_cert_no 从挂号/患者档案带出,不得硬编码。

### P0-4 收费链路未调用 2204 费用明细上传
- 位置:`service/cashier/CashierService.doCharge()` 直接 2206→2207;`OutpatientService.uploadFeeDetail` 仅在 `/api/outpatient/fee-detail` 裸接口暴露,收费主流程不调用。
- 规范依据:5.2.3.6【2204】为结算前置交易,平台按已上传明细做目录审核与金额校验;明细不上传,2206/2207 必被拒(或按平台策略走例外,不可依赖)。
- 修复方向:收费主流程插入 `2204 明细上传(按 chrg_bchno 分组)→ 2206 预结算 → 2207 结算`;表103 必填字段(feedetl_sn、mdtrt_id、psn_no、chrg_bchno、rx_circ_flag=0、fee_ocur_time、med_list_codg、medins_list_codg、det_item_fee_sumamt、cnt、pric、bilg_dept_codg/name、hosp_appr_flag、tcmdrug_used_way、etip_flag、dscg_tkdrug_flag、matn_fee_flag)必须全量填充,布尔类标志位无则传 0;无医保目录编码的明细(自费项目)按平台规则处理(仅传 medins_list_codg 或走自费通道)。

### P0-5 真实模式金额拆分错误(个账被重复计算)
- 位置:`service/cashier/CashierService.java:523`:`selfPay = firstNonNull(bd(setlinfo,"psn_part_amt"), bd(setlinfo,"psn_cash_pay"))`。
- 问题:规范定义 `psn_part_amt 个人负担总金额 = 个人账户支出(acct_pay) + 个人现金支出(psn_cash_pay)`(2207 重点说明第4条:个人账户支出含账户共济)。取 psn_part_amt 作为患者现金自付 → fund + acct + self = fund + acct + (acct + cash) > medfee_sumamt,账单四分不平,退费与对账全部失真。
- 修复方向:selfPay 取 `psn_cash_pay`,缺省时才用 `psn_part_amt - acct_pay` 兜底;落库后加"总额守恒"断言(fund+acct+self=total,不等则告警)。

### P0-6 结算成功但未取到 setl_id 时静默继续
- 位置:`service/cashier/CashierService.java:509-534`。setlinfo 缺失或 setl_id 为空时,真实模式下 fundPay/acctPay/selfPay 全为 0/回退为全额自付,账单照样转"已收费"。
- 修复方向:2207 成功后 `setl_id` 为空必须抛错回滚(无结算ID的医保单不允许落库)。

### P0-7 医保调用与本地事务之间无补偿机制
- 位置:`CashierService.doCharge()`(2207 在事务内)、`refund()`(2208 在事务内)。
- 问题:
  - 2207 成功 → 本地事务随后失败回滚 → 医保平台已结算、院内无收费单(基金已扣、院内无账);
  - 2208 撤销成功 → 本地事务随后失败回滚 → 医保已撤销、院内单据仍是"已收费"。
- 修复方向:(a) 医保调用尽量后置(本地全部落库完成后再调平台,失败时业务可重试);(b) 建立"待冲正"状态表,事务失败时自动触发 2601 冲正或 2208 撤销补偿;(c) 接入 3201/3202 对账兜底(见 P1)。

### P0-8 部分退费不撤销医保结算(医保侧多付)
- 位置:`CashierService.partialRefund()` 明确注释"医保部分退费不线上撤销结算…仅院内退费"(788行、948-950行)。
- 问题:医保已按全额结算,院内部分退费后医保基金多付且不可追,属于合规红线(基金多付=拒付/审计风险)。
- 修复方向:部分退费标准做法:2208 全额撤销 → 2204 按新明细重传(退费明细以负数或新批次)→ 2207 重新结算 → 新 setl_id 回写退费单;或按平台支持的比例退费交易处理。在实现前,应在 UI/接口层**禁止**对医保单做部分退费(只允许全额退),不能静默留线下。

### P0-9 并发竞态:同就诊并发收费/并发退费无行锁
- 位置:`doCharge()` 第1步先读 `charge_status` 后写;`refund()` 先读 `status` 后写。两个收费员同时收费同一就诊 → 双方都通过校验 → 两次 2207 结算(平台侧可能双结算);两个退费并发 → 双 2208。
- 修复方向:收费前 `SELECT ... FOR UPDATE` 锁定 his_visit 行(或对 visit_id 加分布式锁/DB 乐观锁),退款对 his_charge_bill 加行锁;`refund()` 与 `partialRefund()` 需互斥(当前全额退费检查"已部分退"但两接口并发仍可绕过)。

## 三、P1 级问题(规范符合性与医保原生缺口)

### P1-1 2201 挂号交易号与字段集不一致
- 位置:`service/OutpatientService.java:30-41`、`HisRegistrationService:203`。
- 问题:输入含 `med_type`(2201A 新增字段),但 infno 传 `"2201"`。规范接口列表中 2201A 是独立交易编号。对不接受扩展字段的平台会按"多参"拒绝或忽略。
- 修复方向:对接前与省平台确认;稳妥做法是直接传 `infno="2201A"`(V1.2.02 已含该交易)。

### P1-2 opter_type 取值与字典语义不符
- 位置:`application.yml:64` 配置 `opter-type: "2"`,注释写"1-医保经办 2-定点医药机构"(自创字典)。
- 规范依据:表3 `opter_type 经办人类别:1-经办人;2-自助终端;3-移动终端`。HIS 收费员/医生工作站操作应传 **1**。
- 修复方向:默认值改 "1",配置注释改为规范字典;自助机/移动端渠道才传 2/3。

### P1-3 未实现 9001 签到, sign_no 恒为空
- 规范:表3 `sign_no 交易签到流水号,通过签到【9001】交易获取`。湖北省平台普遍要求每日签到,部分交易(结算类)校验签到流水。
- 修复方向:实现 9001 签到(开机/每日定时),签到流水号落库供当日报文头使用。

### P1-4 未实现 1101 人员信息获取(读卡为本地模拟)
- 位置:`HisPatientInsuService.syncFromReadCard()` 直接调用 `mock1101InsuInfo()` 本地造假数据。
- 修复方向:实现 1101(按 mdtrt_cert_type+mdtrt_cert_no 取 psn_no/参保信息/待遇状态),真实读卡后覆盖本地参保档案;参保地 insuplc_admdvs 从这里取(联动 P0-2)。

### P1-5 未实现医保原生审核/对账交易(完整清单)
- 2601 冲正(网络超时补偿,P0-7 的配套交易)
- 3101/3102/3103 明细审核事前分析/事中分析/事前事中反馈(医嘱-处方审核闭环,医保原生核心)
- 3201/3202 费用结算对总账/对明细账(每日对账,医保原生核心)
- 3301/3302 目录对照上传/撤销(对照只维护在院内表,未上传平台 → 平台侧无对照,明细审核与结算可能因目录不可识别被拒)
- 3401 科室信息上传(平台侧科室字典;挂号 2201 传的 dept_code 需先在平台备案)
- 2205 费用明细撤销(退费/撤销结算后的明细清理)
- 2001 待遇享受检查(慢特病/门诊统筹待遇前置校验)
- 9101/医保码一码付(凭证类型 01 场景)
- 修复方向:按规范 5.2.7/5.3 章逐项实现,优先级:3301 目录对照上传 → 3201/3202 对账 → 2601 冲正 → 3101-3103 → 2001。

### P1-6 自费患者无法挂号
- 位置:`HisRegistrationService.register()` 无条件调用 2201(206行),psn_no 为空的自费患者 2201 必失败 → 挂号被拒。
- 修复方向:无 psn_no 时走"院内挂号"分支(不调 2201,mdtrt_id 留空,后续走自费收费);有 psn_no 才走医保挂号。

### P1-7 凭证类型与个人结算方式硬编码
- 位置:`HisRegistrationService:194`(mdtrt_cert_type 兜底 "02")、`CashierService:498`(`mdtrtCertType("02")`)、`CashierService:497`(`psnSetlway("01")`)。
- 问题:不支持电子凭证(01)/社保卡(03);结算时凭证类型应与挂号/读卡时一致,硬编码 02 与患者实际凭证不符时平台会拒。
- 修复方向:凭证类型与凭证编号从患者档案/挂号记录带出,全链路一致;psn_setlway 与平台字典核对后配置化(默认按项目结算)。

### P1-8 fixmedins_code 位数与平台要求核对
- 位置:`application.yml:54` 配 12 位 `H42010000000`;表3 定义定点医药机构编号为字符型 **14** 位。
- 修复方向:以省平台下发编号为准(不足位平台是否要求补零需确认);msgid 取前 12 位逻辑同步核对(机构编号≥13位时截前12位正确性需确认)。

### P1-9 数值型字段为空必须传 0(规范硬性约定)
- 规范 4.4:「类型为数值的参数,如果为空,必须传"0",其他为空串("")」。
- 现状:fastjson2 `JSON.toJSONString` 默认省略 null 字段 → 数值空字段整体缺失而非传 0。
- 修复方向:对医保出入参 DTO 的数值字段统一 `BigDecimal` 非空断言或序列化前补 0(至少 2206/2207/2204 的必填金额字段)。

### P1-10 结算输出未解析 setldetail(基金分项)
- 位置:`dto/SetlInfoResult` 仅含 setlinfo 聚合字段;`SetlResultHandler` 只存聚合。
- 影响:统筹/大病/救助等基金分项(fund_pay_type/fund_payamt)不入库,对账 3202 与界面分项展示无数据源。
- 修复方向:解析 setldetail 数组并落库(新增 his_setl_fund_item 表),与 3201/3202 对账联动。

### P1-11 退费后就诊无法重新收费
- 位置:`doCharge()` 校验 `charge_status=2` 直接拒绝(420-422行)。
- 问题:全额退费后(改处方/换药场景)需重新收费,当前只能重新挂号就诊;且 2208 撤销后费用明细未走 2205 撤销,重传时 feedetl_sn 会重号。
- 修复方向:增加"退费后重新收费"路径:允许 charge_status 2→0(有退费单即放行),重新收费前先 2205 撤销明细再 2204 重传。

### P1-12 响应报文未验签 / signtype 未发送
- 规范:输出报文同样携带 cainfo;表3 `signtype 签名类型(建议SM2、SM3)`,部分平台校验该字段。
- 修复方向:实现 SM2 验签(公钥验平台签名,可选开关);报文头补发 `signtype`(与省平台确认取值)。

## 四、P2 级问题(健壮性)

- msgid 顺序号内存计数:进程重启归零,同秒内撞号概率存在;顺序号 wrap 后同日同秒可能重复(SEQ 循环 9999→1)。建议 msgid 顺序号落库(按天+机构取号)。
- Mock 结算输出金额用字符串("10.00")而非数值,真实平台为数值型,建议 Mock 与真实格式一致。
- 挂号成功后未校验返回 mdtrt_id 非空(HisRegistrationService:211-215),mdtrt_id 为空仍落库。
- `buildRequest` 中 fixmedins_code 补零左对齐逻辑(11位以下补0)与 14 位定义不一致,统一按平台下发码处理。
- 医保裸接口 `/api/outpatient/*`(2204/2206/2207/2208 等)未挂业务权限与机构校验,任何登录用户可直接向平台发起结算/撤销,必须加权限与状态机守卫(见多租户审计篇)。

## 六、医保原生架构优化建议(升级路线)

1. **对账驱动闭环**:以 3201/3202 每日对账为核心,结算成功/撤销/冲正全部落 `his_setl_record`(已有)+ `his_setl_fund_item`(新增),对账不平自动告警并生成 2601 冲正候选。
2. **目录对照闭环**:3301 上传改造为对照变更事件驱动(对照新增/失效即上传),与 1301~1307 下载形成双向闭环;对照失效清单作为结算前置拦截。
3. **事前事中审核**:处方保存/收费前调 3101 事前分析、收费时调 3102 事中分析、按 3103 反馈结果决定"继续/返回修改",审核结果落处方/收费单留痕。
4. **状态机独立化**:引入"医保交易状态机"(挂号→就诊上传→明细上传→预结算→结算→撤销),每步状态落库,驱动院内业务状态,而不是院内状态隐式驱动医保调用。
