- 10,000 个压测患者(LT 前缀)、排班 129 号源放量、发药仓库存放量;mock 医保模式(每链约 5 笔医保交易)

### 容量测算模型
- 5000/日按门诊高峰 15% 计: 高峰小时 750 人次 = 平均 12.5 链/min, 突发分钟约 32 链/min
- 实测吞吐(mock 模式): c=10 2241 链/min, **c=25 3445 链/min(0 错误)**, c=50 3022 链/min(0 错误), 挂号专项 c=50 6000 笔/min
- 即压测吞吐 ≈ 峰值需求(32 链/min)的 100 倍
- MySQL 全程: 连接 ≤71、运行 ≤21、**慢查询(>2s)= 0**;Hikari 20 连接池从未耗尽
- 真实医保平台测算: 每链 5 笔医保调用 × 0.5~2s 平台延迟 = 2.5~10s/链, 峰值 32 链/min 仅需 2~6 个并发收费链路 —— 应用侧与连接池余量充足, 瓶颈将在平台侧而非本系统

### 压测发现并修复的生产 BUG(3 个 + 1 个设计修正)
1. **完成接诊死锁(严重, 2146 次/轮)**: `HisDiagnosisService.saveDiagnoses` 先删后插, RR 隔离级别下并发完成接诊互相抢 idx_visit 间隙锁 → InnoDB 死锁, 首轮 c=50 下 361/1750/2149 链失败。修复: `HisVisitService.finishVisit` T1 改 READ_COMMITTED 隔离(TransactionTemplate) + 死锁整体重试(≤3 次) + 状态条件抢占(baseMapper.update 判 affected, 注意 ServiceImpl.update(Wrapper) 返回 boolean 而非行数);2203 上传移出事务(原实现医保调用持库连接数秒)。修复后 c=50 全量 2267 链 0 死锁
2. **收费单号回绕(严重, 单日第 10000 单起全线故障)**: `CashierService.generateBillNo` 用 `Math.floorMod(seq, 10000)`, 单日超 9999 单后回绕与已有单号撞 uk_tenant_bill_no → Duplicate entry, 20 并发收费全部失败(裸"系统异常")。修复: 去掉回绕, 序号自然进位 5~6 位(惰性续接 SQL 的 SUBSTRING(bill_no,11) 取后段仍兼容)
3. **候诊序号重号(压测复现 74% 行重复)**: `HisRegistrationService.generateQueueNo` 裸 MAX+1, 并发下大面积同号。修复: 按 租户|科室|时段|日期 内存 AtomicInteger 计数(首次从 DB MAX 惰性播种, 重启/换日自动续接), 与 bill_no SEQ 同模式。验证: c=20 连续 3000 笔挂号 0 重复
4. **并发收费守卫验证(正确行为)**: 同就诊 20 线程并发收费突刺 → 恰 1 成功(156ms)/19 被 T1 行锁 + 结算中守卫干净阻断, 无双收费、无漏收费、无原始 SQL 报错

### 遗留提示(非阻塞)
- bill_no/queue_no 内存序列为单实例设计;多实例部署需单点生成或加唯一键+重试兜底(bill_no 已有 uk 兜底会转报错, queue_no 无唯一键会静默重号)
- 挂号 genNo 为 timeCompact+AtomicInteger%1000, 超 1000 笔/秒回绕(无唯一键, 仅影响号面美观)
- 压测数据(1 万 LT 患者、2 万余挂号/收费单、排班与库存放量)仍留在库中, 正式上线前需清理或迁移
