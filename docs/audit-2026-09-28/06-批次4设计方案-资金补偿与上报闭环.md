## 二、总体架构:医保交易状态机 + 交易日志 + 补偿引擎

### 2.1 核心原则

1. **外部调用后置、分段提交**:任何医保写交易(2204/2206/2207/2208/2202/2205)不得持有本地行锁执行网络 IO。流程拆三段:
   - **T1 本地事务**:行锁校验 + 建单据(中间态)+ 提交释放锁;
   - **T2 医保调用**:独立于本地事务(网络 IO,带超时);
   - **T3 本地事务**:按 T2 结果条件更新单据终态(幂等,affected-rows 判成败)。
2. **结果三分**:T2 结果区分 SUCCESS(平台明确回执)/FAIL(平台明确拒绝)/**UNKNOWN(超时或网络异常,平台侧状态未知)**。UNKNOWN 是补偿引擎的主战场。
3. **事实来源唯一**:平台侧状态以 `setl_record`(2207/2208 回执落库)为准;未知态以 3202 对账定位;最后手段 2601 冲正。

### 2.2 新增基础表(DDL 详见 §八)

| 表 | 用途 |
|---|---|
| `his_yb_txn_log` | 全部医保出站交易日志(infno/msgid/关键业务键/状态/重试)——2601 omsgid 的唯一来源 |
| `his_comp_task` | 补偿任务(重试/补录/冲正),定时扫描驱动 |
| `his_upload_status` | 上传管线状态机(2203/2301/2201 等逐单状态) |
| `his_yb_upload_queue` | 3301/3302 对照上传队列 |
| `his_recon_task` / `his_recon_diff` | 3201/3202 对账任务与差异明细 |
| `his_charge_bill` 加列 | `yb_status`:0 未结算 / 1 结算中 / 2 已结算 / 3 撤销中 / 4 已撤销 / 9 冲正中(与 `status` 收费状态正交) |

### 2.3 交易日志写入点

`YbHttpClient.call()` 统一落 `his_yb_txn_log`(所有 infno 出站都记,与 mock/real 无关,tenant 由 UserContext/TenantContext 带出):
- 发报文前记 `PENDING`(infno/msgid/机构/时间/input 摘要);
- 平台回执 → `SUCCESS`(回执码 0)或 `FAIL`(回执码非 0,记 errMsg);
- HTTP 层 IOException / 读超时 → `UNKNOWN`(平台侧状态不可知,这是与 FAIL 的本质区别);
- 补偿/冲正落 `REVERSED`。
业务键(mdtrt_id/psn_no/setl_id/chrg_bchno/bill_id)由上层回调回填,或从 input JSON 抽取(统一约定:input 内 `data` 节点的这些字段)。

## 三、模块 A7:2207/2208 补偿中间态 + 2601 冲正

### 3.1 收费两阶段化(改造 `doCharge` 医保分支)

现状:整个 `doCharge` 一个 @Transactional,2204→2206→2207 全部在事务内。改造:

```
T1(事务A)  锁 his_visit FOR UPDATE → 校验 → 建 bill(status=0, yb_status=0) + 明细 → 提交
T2(无事务) 2204 → 2206 → 2207(每次调用前查 txn_log 避免重发;同批 chrg_bchno=bill.billNo)
T3(事务B)  按 T2 结果:
  SUCCESS → bill 条件更新(0→1)回填四分金额/setl_id;charge_status 0→1 条件更新;后续下游联动
  FAIL    → bill 标记作废(status=-1,yb_status=0);就诊可重新收费(明细原样保留)
  UNKNOWN → bill 留 status=0, yb_status=1(结算中);生成补偿任务
```

**并发语义不变**:T1 的行锁只在本地落库窗口持有,提交即释放;第二次收费进入 T1 时读到 charge_status=1 或 yb_status=1 → 拒绝("收费处理中,请稍后查看结果")。

### 3.2 UNKNOWN 处置决策树(收费)

```
txn UNKNOWN(2207 超时)
 └─ 补偿任务(指数退避 1/5/15/60min, max 6 次后转人工)
     ├─ 先查平台侧事实:3202 对账定位(或平台提供的结算查询接口,联调确认)
     │    ├─ 平台已结算 → 补 T3(幂等条件更新,直接置已收费)
     │    ├─ 平台无记录 → 允许重试 T2(2204 重传前先 2205 撤旧明细,防 feedetl_sn 重号)
     │    └─ 无法定位(对账当天未跑/平台无查询) → 执行 2601 冲正(见 3.4)后重试 T2
     └─ 冲正后 3202 复核:平台侧该笔消失 → 冲正生效
```

### 3.3 退费两阶段化(改造 `refund`)

```
T1(事务A)  锁原单 FOR UPDATE → 校验(机构/日结/部分退互斥)→ 建退费单(status=0)
           + 复制明细 + 负向支付明细 → 原单置 yb_status=3(撤销中)→ 提交
T2(无事务) 2208(超时即 UNKNOWN,绝不重发——2208 重复会撤错或拒)
T3(事务B)  按 T2:
  SUCCESS → 原单条件更新(1→2) + 退费单 0→1 + charge_status 1→2 + 发票红冲
  FAIL    → 原单 yb_status 3→2(回已结算);退费单标记作废
  UNKNOWN → 退费单留 status=0;补偿任务走 3.2 同款决策树(平台已撤→补 T3;未撤→重试 2208)
```

**关键点**:T1 提交后窗口期,原单仍是 status=1 可被另一窗口全额退 → 并发互斥由 yb_status=3 守卫(退费入口校验:yb_status ∈ {0,2} 才可退)。

### 3.4 2601 冲正(规范 5.2.7.1,严格照抄)

- **可冲正清单**(规范原文):2102/2103/2207/2208/2304/2305/2401/2304A/2102A —— 门诊收费/退费在列 ✓。
- **输入(节点 data,单行,仅 3 字段)**:
  - `psn_no` 人员编号(字符 30,Y)——原发送方报文的 psn_no;
  - `omsgid` 原发送方报文 ID(字符 30,Y)——**取原交易的 msgid,从 `his_yb_txn_log` 取**;
  - `oinfno` 原交易编号(字符 5,Y)——如 `2207`/`2208`。
- **输出:无**。冲正成功无回执内容 → 必须以 3202 对账复核冲正是否生效,不能仅凭调用无异常即认为冲正完成。
- 触发条件:平台侧多数据(有结算无本地单、撤销超时后平台仍持有结算),且本地无法补录/重试时。
- 冲正后:原交易在平台侧被取消 → 本地可安全重试整条链(2204 重传→2206→2207),明细先 2205 撤销。

### 3.5 收费入口守卫补充

- 收费前校验 2203 就诊上传状态(联动 A13,见 §六):`his_upload_status` 中 VISIT 未传成功 → 先补传 2203,成功才继续 2204/2206/2207(规范顺序:就诊上传是结算前置)。

## 四、模块 A8:部分退费线上化 —— "全撤重结"

### 4.1 方案选择与依据

规范事实:2205 明细撤销"**已参与结算的明细不能撤销**";平台侧无"部分撤销结算"交易。因此部分退费唯一合规路径 = **全撤重结**:

```
T1(事务A)  锁原单 → 建部分退费单(status=0, billType=2, 退费金额=选中明细)
           + 原单 yb_status=3 → 提交
T2(无事务) ① 2208 撤销原结算(setl_id/mdtrt_id/psn_no)
           ② 2205 撤销明细(mdtrt_id + chrg_bchno=原批次或"0000"全撤未结算明细 + psn_no)
           ③ 2204 重传剩余明细(新 chrg_bchno=重结单号;退掉的明细不再传)
           ④ 2206 预结算(medfee_sumamt=剩余明细金额)
           ⑤ 2207 重结算 → 新 setl_id
T3(事务B)  原单 1→2;部分退费单 0→1;新建"重结收费单"(billType=1,status=1,setl_id=新,
           totalAmount=剩余金额,remark 标注"部分退费重结, 原单 xxx")
           → 就诊 charge_status:剩余金额>0 保持 1,=0 置 2
```

### 4.2 各步失败处置

| 步骤 | FAIL | UNKNOWN |
|---|---|---|
| ①2208 | 原单回 yb_status=2,退费单作废 | 走 §3.3 UNKNOWN 决策树,确认撤销后再继续 |
| ②2205 | 重试(幂等:全撤语义) | 重试;已撤重复撤平台侧按无明细处理(联调确认) |
| ③2204 | 重试前先 2205 全撤,防 feedetl_sn 重号 | 同上 |
| ④⑤2206/2207 | 退费单与重结单都留中间态,补偿重试 2206/2207(明细已在平台,直接重结算) | 走 §3.2 决策树 |

### 4.3 前置守卫

1. 退费明细若含已发药药品(P1-14 联动):先退药再退费,否则拒绝("药品已发药,请先到药房退药");
2. 已执行治疗/检验项目不允许退(执行单状态校验);
3. UI 部分退费确认框提示语改为:"部分退费将线上撤销医保结算并按剩余明细重新结算(全撤重结),预计耗时增加数秒"。

## 五、模块:3201/3202 对账与日结口径

### 5.1 3201 对总账(规范 5.3.2.1)

- **每日定时**(默认 07:00 对 T-1,可配),按 `insutype` 分组逐险种发起;
- 输入(节点 data,单行,字段照表 196 全列):
  - `insutype` 险种(Y,6)/`clr_type` 清算类别(Y,6)/`setl_optins` 结算经办机构(Y,6)——**三者取值以平台下发的定点配置与规范第 6 章值域为准,实施时配置化,不硬编码**;
  - `stmt_begndate`/`stmt_enddate`(Y,日期型,以结算时间 `setl_time` 为依据);
  - `medfee_sumamt`/`fund_pay_sumamt`/`acct_pay`(Y,16,2)——本地口径:`setl_record` 按 `status=1` 加、`status=0` 减(退费冲抵),与 `his_charge_bill` 交叉校验;
  - `fixmedins_setl_cnt` 定点医药机构结算笔数(Y,数值 10)——结算笔数-撤销笔数;
  - `refd_setl_flag` 退费结算标志(Y,6,取值与平台确认)。
- 输出(节点 `stmtinfo`):`setl_optins`/`stmt_rslt` 对账结果/`stmt_rslt_dscr` 说明 → 落 `his_recon_task`。

### 5.2 3202 对明细账(规范 5.3.2.2,总账不平才跑)

- 生成明细 TXT(TAB 分隔、UTF-8、空值 `null`、列序按规范表 199 输入文件参数说明逐列转录,**退费数据传正向+反向两条**——规范重点说明 2)→ ZIP → **9101 上传** → 取 `file_qury_no`;
- 3202 输入(节点 data,单行):`setl_optins`/`file_qury_no`/`stmt_begndate`/`stmt_enddate`/`medfee_sumamt`/`fund_pay_sumamt`/`cash_payamt`(Y)/`fixmedins_setl_cnt`/`clr_type`/`refd_setl_flag`(长度 3,注意与 3201 的 6 不同,照规范)/`exp_content`;
- 输出(节点 `fileinfo`)差异清单落 `his_recon_diff`;中心端多条明细时结算 ID/就诊 ID 为空(规范重点说明 7)→ 差异按金额逐笔人工核对。

### 5.3 9101 文件上传(规范 5.8.2.1,3202/3301 共用底座)

- 输入(节点 `fsUploadIn`):`in` 文件数据(字节数组,Y)/`filename`(200,Y)/`fixmedins_code`(30,Y);
- 输出:`file_qury_no`/`filename`/`fixmedins_code`/`dld_endtime`;
- 复用 `DictDownloadService` 的流式 ZIP 思路(反向:本地上传);filename 命名规则联调确认。

### 5.4 日结口径修复(P1-15)

1. **挂号费纳入**:挂号收款时生成挂号收费流水(`his_reg_payment`:reg_id/org_id/渠道/金额/时间),日结汇总 = `his_charge_bill`(cash/fund/acct 按渠道)+ `his_reg_payment` 分项,报表增"挂号费"行;退号退款生成负向流水(P1-18 账务留痕一并解决);

3. 日结已锁定的退费互斥逻辑保持不变(现有 `HisDailySettle` 判断正确)。

### 5.5 对账闭环输出

- 平 → 记 `his_recon_task` 成功;
- 不平 → 告警 + 自动 3202 → 差异落库 → 人工处理(补传/冲正/退费);冲正候选生成条件:平台有结算、本地无单据,且无法补录。

## 八、DDL 草案

```sql
-- 医保出站交易日志(2601 omsgid 来源; 全部 infno 出站统一落)
CREATE TABLE his_yb_txn_log (
  id BIGINT NOT NULL AUTO_INCREMENT,
```

## 十、联调前置确认清单(与省平台确认后冻结实施细节)

1. `list_type` 目录类别值域(3301 必填字典,药品/诊疗/耗材的规范代码);
2. `clr_type` 清算类别、`setl_optins` 结算经办机构、`refd_setl_flag` 取值(3201/3202 必填字典,注意 3201 长度 6 与 3202 长度 3 的差异按规范);
3. 3301 上传后平台审核状态的获取途径(3301 输出无;是否经查询交易/3302 语义反推);
4. 2208 撤销后同一 mdtrt_id 重新 2204→2206→2207 重结算的平台支持性(A8 前提);
5. 2601 冲正后的确认方式(输出无 → 3202 复核的口径);
6. `omsgid` 复用原 msgid 的格式要求(原 msgid = 机构12位+yyyyMMddHHmmss14+顺序4,共 30 位,与 2601 字段长度 30 匹配);
7. 3202 明细文件列序(规范表 199 输入文件参数说明逐列转录)与 9101 filename 命名规则;
8. 3301 每批 100 条上限与超限分页口径;
9. 2205 重复撤销(chrg_bchno="0000" 全撤)的平台幂等性;
10. 2301 处方上传在本机构场景(院内门诊处方上报 vs 药店购药)的适用性。
